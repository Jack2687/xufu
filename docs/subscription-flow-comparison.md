# 订阅办理：旧流程与新流程

后台“支付全监控 → 订阅流程配置”或“代理管理 → 付款配置”可选择：

- **旧流程 · 原版提链与网页付款**（`legacy`）
- **新流程 · cs-live 订阅办理**（`cslive`）

默认保持升级前正在使用的新流程。保存只影响之后新建的订阅订单；网页与 Space 等 API 客户端使用同一后台选择，无需修改接口参数。已经受理、排队、待验证或待核实的订单继续原流程，重复请求也返回原订单，不切换、重建或重新冻结服务费。独立提链、独立续费管理不受开关影响。

旧版来源为本地 `before-subscription-rewrite-20261028-203008/source-and-config.zip`，基线提交 `7e1dfd40ec01463a0265985f1b54c90daaa18487`。复用备份中保留的业务实现：`checkout_provider.go`、`provider_session.go`、`subscription_status.go`、`runtime/payment-browser.mjs` 内容一致；订阅提链、浏览器付款和付款后续费任务的原有顺序保持。仅在受理时选择整套执行路径，不混用两套付款方法，也不把失败自动切到另一套。

| 顺序 / 环节 | 旧流程：备份中的原版 | 新流程：当前 cs-live 接入 |
| --- | --- | --- |
| 1. 提交、排队 | 校验 Session、卡片、套餐与地区；幂等受理、同账号互斥、冻结服务费，排队获取资源 | 同一套平台受理、资金和队列规则 |
| 2. 账单和代理 | 后台正式资料随机选一份并保存加密快照；绑定订单代理，后续复用 | 同一套正式账单池和订单代理规则 |
| 3. 提链前授权 | 使用仍有效的 accessToken；不提前刷新，接受 AT-only | 要求 sessionToken / 有效会话 Cookie；提链前刷新，支持有效刷新凭据接续过期 AT |
| 4. 开头查账号 / 套餐 | 在线确认账号归属及个人账号，查有无有效订阅；已有订阅直接停止 | 在线核对账号及当前订阅基线；检查冲突，支持原包限定的 Plus → Pro 5x 升级分支 |
| 5. 生成结账链接 | 原提链请求生成 Hosted 长链接；订阅办理固定长链，独立工具仍可选长短链 | 原包初始化并创建 Checkout，按实际 Hosted / Custom 返回进入分支；升级分支不新建 Checkout |
| 6. 填卡、账单、税费 | 服务器私有 Chromium 打开官方付款页，填卡及本单账单，等待官方页面返回最终税费和报价 | 原包处理付款页上下文、账单与税费，建立付款方式或确认令牌，读取报价；具体步骤随付款分支而定 |
| 7. 提交付款 | 核对报价/币种和原出口，服务器自动确认，点击官方页面的提交按钮；阻止再次提交 | 按原包付款分支提交，关键请求前保存加密检查点；未知结果不重新确认付款 |
| 8. 付款结果 / 额外验证 | 读取原结账响应中的权威付款证据；明确拒付失败，待验证/未知暂停，旧核实入口只查原单 | 原包区分扣款、授权、处理中、拒付及待验证；待验证自动接续官方 SDK，再 Recover 核实原交易；官方实际要求的交互不能伪造 |
| 9. 核实订阅生效 | **已有**：付款成功后查有效订阅并匹配所购套餐；默认间隔 5 秒、最多 12 次，可配置。查询 401 且有刷新凭据时刷新重查 | **已有**：核对有效订阅和套餐，按原包最多 5 次、间隔 2 秒；401 刷新重查 |
| 10. 取消前刷新 Session | **已有**：生效确认后进入取消阶段，再主动刷新并重新查询；AT-only 旧输入无法刷新，只能沿用有效 AT | **已有**：生效确认后再次主动刷新，然后查询续费状态 |
| 11. 取消自动续费 | 已关闭直接完成；否则持久标记后最多提交一次取消，再查询 `will_renew=false`。结果未知只复查；默认 30 秒、最多 10 次，可配置 | 已关闭直接完成；否则按原包取消并有限复查。原包在特定瞬时失败且查询仍开启时允许第二次取消提交 |
| 12. 保留续费 / 完成 | 选择保留时仍核实生效，但不执行取消；付款、生效、续费结果分别记录 | 相同结果要求，由原包后续处理实现 |
| 13. 恢复与重启 | 使用原结账、原代理查付款；付款后独立持久任务核实生效/续费，不恢复卡号、CVV或重复付款 | 使用原加密检查点 Recover，可能接续原交易批准动作，再核实生效/续费；不重新提链或重新确认付款 |
| 14. 网络异常 | 保留原版付款前安全重建选项：仅明确未提交且满足条件时允许换会话重新准备；已提交/未知/成功不换出口重付 | 会话到期、缺失或出口变化即停止，不自动换会话；全链条请求检查原出口与租约 |
| 15. 监控与客户显示 | 管理员可看本单“旧流程”、账单快照、链接及脱敏阶段；客户固定七步 | 管理员可看本单“新流程”，另有协议与 SDK 诊断；客户同样固定七步 |

客户七步保持：**提交申请 → 排队准备 → 办理准备 → 订阅付款 → 订阅生效 → 取消自动续费 → 办理完成**。两套核心调用均在服务器执行；客户不接收后台选择、上游核心请求、检查点、平台代理凭据或实际账单快照。

## 旧流程可补充的事项（本次未改变原版业务逻辑）

1. **把“开头查套餐”做得更细**：旧版已判断是否有有效订阅，但没有新流程的完整订阅基线与升级判定。若希望已有 Plus 自动升 Pro 5x，需要单独补充升级策略，不能仅允许继续创建普通结账单。
2. **统一要求可刷新的完整 Session**：旧版已有生效检查和取消前刷新，但仍兼容 AT-only。若要求每单都必须刷新后取消，应在受理时要求刷新凭据，避免付款后才发现无法刷新。
3. **额外验证接续**：旧版遇到待验证会暂停，不能称旧版已具有新流程的 SDK 自动接续能力。需要时应按原交易实现受支持的接续入口，不再次付款。
4. **明确付款前换会话策略**：若“每单一个 IP”连明确未付款的准备失败也不允许换，旧流程可将“付款前网络会话最多重建次数”设为 0；本次保留原配置，没有擅自更改。

生效核实和取消前刷新已经存在，不需要重复增加一套。是否成功始终以真实付款、套餐生效及续费查询结果为准，不能用页面跳转、按钮点击或 SDK 回调替代。

## 持久化与权限

`payment.subscription_flow` 为管理员配置，受理事务在付款配置行上加共享锁，并在同一事务里决定是否创建 `subscription_protocol`。此记录的存在与否固定原订单使用的执行器；执行、核实与重启均读取订单记录。历史订单按既有记录识别，不迁移、不重放。旧管理页面未传新字段时保留已有值；启动迁移仅补缺省值。非法值拒绝受理，普通客户不能改配置，客户详情/API 不输出此内部标识。
