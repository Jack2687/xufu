# 核心流程与调度边界

更新于 2026-10-28。新订阅使用 [cs-live 协议流程](subscription-protocol.md)，核心调用全部服务端执行；客户页面只调用本站业务 API。

## 输入与输出

- Session 格式检查只检查结构、账号一致性与期限，返回 online_verified=false；新订阅要求刷新凭据，在线刷新和身份核对在服务端办理准备中完成。原始 Session JSON 不保存，最小授权及检查点 AES-GCM 加密保存，最长 24 小时。
- 卡号/CVV 提交后清空客户端输入，仅在本次内存使用，不进入数据库、日志、浏览器存储或检查点。旧单兼容付款进程通过私有管道接收输入。订单只返回卡片尾号、金额和业务状态。
- 账单从后台已启用、非测试且完整的正式池均匀随机抽取，每单保存加密副本；不按邮箱绑定、不编造身份或按税率筛选。同单重试、恢复及后台编辑不会换资料，缺失资料在冻结/提链前拒绝。
- 客户仅看到“提交申请 → 排队准备 → 办理准备 → 订阅付款 → 订阅生效 → 取消自动续费 → 办理完成”。选择保留时第六步标题保持，下方注明“已选择保留”；异常显示待核实，不假完成。
- 客户网页及 API key 不能取得订阅结账 URL、核心路径、检查点、报文、平台凭据、完整账单或其他客户数据。管理员支付全监控只返回白名单诊断，以及授权保留的实际结账链接历史；不返回原始报文或秘密。
- 本人提交的 Session 和卡片可以在本人的请求中看到。隐藏的是服务器与上游的调用过程，不能承诺隐藏用户自己的输入，也不涵盖服务器/root 访问。

## 提交、资金与恢复

订阅受理使用幂等键、账号互斥、事务锁与容量限制，先冻结服务费，再将卡片放入本次内存等待队列。无同地区空闲代理则等待，不直连；进程重启无法恢复卡片，不自动重付。旧 worker 通过租约 fencing 被拒绝。

新订阅由同一订单任务调用 Pay 完成刷新、核对、提链、税费和付款；待验证时自动执行原包官方 SDK，再调用 Recover 核实付款并继续后续步骤。实际金额和币种通过本站授权检查后才提交；不可安全重放的动作先同步保存加密检查点。付款方式创建、SDK回调、页面跳转、仅授权或通知轮询均不能代替已扣款证据。

已扣款状态和服务费结算在同一事务幂等落库，不等待取消续费。明确未付款/拒付可解冻，已提交且未知继续冻结；未知、成功、额外验证都禁止重建扣款。恢复查询原交易并可接续其批准、生效和续费处理，不创建新 Checkout、不重新提交银行卡确认。授权或原代理失效时停止接续。

付款、生效、续费各有状态，后两项失败保留已付款。新协议取消前持久化检查点，按原包在瞬时失败后先查询、仍开启才有限重试；旧单和独立续费保留既有单次提交保护。只有有效订阅且 will_renew=false 才确认关闭。官方验证在服务端自动接续；真正需要持卡人交互时保留待核实，管理员可使用受权限限制的异常处理窗口，不能假定所有挑战都能自动通过。

## 网络与权限

新订阅从提链到付款、生效、刷新、取消及复查全部使用同一订单代理会话和出口 IP。每次 HTTP 尝试前核对出口、执行/容量租约、代理有效期及启停状态；漂移即停，禁止直连兜底或自动重建。请求目标限 HTTPS 官方服务白名单。Windows 可使用本机外层代理连接供应商，最终出口仍是订单代理。

独立“结账链接”工具保留原实现，向本人返回生成链接；客户主动打开后，上游页面的请求自然可见。独立“续费管理”工具仍走后台全局代理；接续取消时保留既有提交标记。旧订单保留原兼容路径和历史记录，不冒充新协议。

已有 HttpOnly/SameSite 会话、bcrypt、API key 哈希、逐接口管理员校验、管理员 JS 权限校验、同源检查、CSP、大小限制、资源加密、事务、限流及审计。付款全监控仅管理员可访问，不能用监控接口提交他人银行卡付款。

## 验证范围

隔离 PostgreSQL 与模拟上游测试覆盖 Pay/Recover、未知结果保护、租约、固定 IP、随机账单副本、资金幂等、仅授权/拒付/额外验证、角色与 API key 投影、诊断脱敏。浏览器验收使用本机模拟订单，未真实扣款或取消订阅。详见 [验证记录](verification.md)。
